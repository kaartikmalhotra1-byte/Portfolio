Agentic experiences that are designed around correcting.

What a 10x drop cap taught us about building agentic products that recover well.

MonotypeHAI

14th Nov '26

The claim

Most agentic products are designed to get it right the first time. Accuracy is the metric, and every mistake is treated as a failure to minimise. That's the wrong target. Agents will be wrong, and often they'll be wrong because the user was right to break the rule. An agentic product's real quality is how cheaply it recovers when it's wrong. I learned this building Brand Type Fidelity (BTF), a feature in our Adobe plugin where an agent checks every text layer against a company's typography guidelines and flags breaches in real time.

The designer who broke the rule on purpose

A magazine designer was laying out a quarterly issue. To open a feature article, he set the first letter roughly ten times larger than the body text: a drop cap, there to give the page weight and a clear starting point. It broke his company's type guidelines. It was also the right call. Before BTF, that one decision cost him four or five meetings. First the creative director, then the executive creative director, and each time he explained the same choice from scratch. Nothing in the process remembered why he'd made it. That's the human version of an agent's repeat flag: being asked to justify a deliberate decision again and again.

Error or intent?

BTF flagged the drop cap correctly. The size was outside the guideline. But detection was never the hard part. The hard part is that a breach can be a mistake or a decision, and the agent can't tell which. If it treats both the same, it punishes the designer for using judgment. So the most important thing a user does in an agentic product isn't accepting a fix. It's correcting the agent's read of what they meant. The designer did exactly that. He marked the drop cap as an exception and gave a reason: creative freedom. For the first time, the system recorded not just “ignore this” but why.

When a correction is too broad

Here's where it broke. InDesign lets one text frame hold several font metrics. A drop cap and its body copy usually sit in the same frame. Adobe only let us act on the frame ID, so the exception covered the entire frame, not just the drop cap. The designer had also taken a few more liberties in that same frame, ones he never declared. The frame-level exception hid them all. BTF rolls up a typography status for every document, and the project admin sees the health of the whole project at a glance. This document showed healthy. It wasn't. The tool that should have shortened the review made it worse. The admin trusted the status, the review leaned on it, and the real issues only came out in the room. They had slipped through the cracks. A correction that's too broad doesn't just fail. It makes the system confidently wrong, and that error travels upstream to people who never saw the original decision. The same mismatch hit fixes too. Our agent could detect a breach on specific characters, but we could only fix or exempt at the frame level. Applying the fix wiped out the drop cap. Marking an exception hid real errors. Both options did damage. Correction has to work at the same level as detection. If the agent can see precisely but the user can only act bluntly, every correction becomes a trade-off between destroying intent and hiding errors.

What we built

1. The agent says where its precision runs out. Adobe pins annotations to a frame's top-left corner and won't let us point at specific text inside it. So the breach card says it plainly: this breach sits in a frame with multiple font metrics. It quotes the exact text causing it. And clicking the annotation makes the layer bounce, so the eye finds it. 2. The human sets the scope, the agent does the work. The user selects the specific text, then chooses one of three options: - Apply the recommended fix - Apply a different guideline - Mark it as an exception The middle option is the underrated one. It lets the user say: you were right that something's off, but wrong about the fix. That's richer feedback than yes or no. 3. Preview before commit. On the breach card, click and hold to preview. The corrected metrics apply only while you hold. You see the reflow, the orphaned lines, the knock-on effect on the page, and nothing is committed. A wrong fix costs one released finger, not an undo hunt. The cheapest recovery is the one you never need. 4. Exceptions set a precedent. When a designer marks a specific metric combination as an exception (font size, line height and letter spacing together), that combination is approved anywhere it appears in the document. One decision, made once, carries forward. Precedents are scoped to the document, and the next issue starts fresh. That's deliberate for now, and it's the next thing to get right.

Back to the designer

We shipped the text-level update in beta, built first for his company because that's where the problem surfaced. His response: “It really understands what's going on in the document now. It doesn't just flag what's wrong, it takes my feedback at the level I'm giving it.” That's the whole thesis, in a user's words.

How we'll know if we're wrong

BTF is still in beta, so this is a hypothesis with instrumentation, not a victory lap. We're tracking three signals: - Override mix: how often users pick fix, alternative guideline, or exception. A healthy spread means real judgment calls are happening, not just reflexive dismissals. - Repeat flags: whether a precedent actually stops the same intentional choice from being flagged again. - Preview-to-commit ratio: how often a preview ends without applying. Every one of those is a bad fix avoided. If exceptions dominate the mix, our detection is too strict. If repeat flags don't fall, precedent isn't working. Either way, we'll know.

The principle

Design agents for the moment they're wrong, not just the moment they're right: 1. Treat correction as a signal of intent, not a rejection. 2. Let users correct at the same level the agent detects. 3. Make the cost of a correction visible before it's committed. 4. Say plainly where the agent's precision runs out. 5. Let one correction set a precedent, so nobody defends the same decision five times.
