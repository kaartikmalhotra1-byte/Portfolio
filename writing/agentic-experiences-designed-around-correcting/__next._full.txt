The designer had also taken a few more liberties in that same frame, ones he never declared. The frame-level exception hid them all.

BTF rolls up a typography status for every document, and the project admin sees the health of the whole project at a glance. This document showed healthy. It wasn't.

The tool that should have shortened the review made it worse. The admin trusted the status, the review leaned on it, and the real issues only came out in the room. They had slipped through the cracks.

A correction that's too broad doesn't just fail. It makes the system confidently wrong, and that error travels upstream to people who never saw the original decision.

The same mismatch hit fixes too. Our agent could detect a breach on specific characters, but we could only fix or exempt at the frame level. Applying the fix wiped out the drop cap. Marking an exception hid real errors. Both options did damage.

Correction has to work at the same level as detection. 2. The human sets the scope, the agent does the work. The user selects the specific text, then chooses one of three options:

- Apply the recommended fix
- Apply a different guideline
- Mark it as an exception

The middle option is the underrated one. It lets the user say: you were right that something's off, but wrong about the fix. That's richer feedback than yes or no.

3. Preview before commit. On the breach card, click and hold to preview. The corrected metrics apply only while you hold. You see the reflow, the orphaned lines, the knock-on effect on the page, and nothing is committed. A wrong fix costs one released finger, not an undo hunt.

The cheapest recovery is the one you never need.

4. Exceptions set a precedent. When a designer marks a specific metric combination as an exception (font size, line height and letter spacing together), that combination is approved anywhere it appears in the document. One decision, made once, carries forward. Precedents are scoped to the document, and the next issue starts fresh.
